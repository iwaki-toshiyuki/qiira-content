## **SQLアンチパターンとは？？**

一見すると正しそうに見えるが、実際には問題を引き起こす可能性が高い設計や書き方のこと。

## 代表的なSQLアンチパターンとは？？


### **① ゴッドオブジェクト（God Object）**

**概要**

あらゆるデータを1つの巨大なテーブルに格納しようとするアンチパターン

**❌ 悪い設計**

```
big_table
-----------------------------------------
id
user_name
user_email
product_name
product_price
order_date
order_status
shipping_address
```

**顧客・商品・注文を全部1テーブルに入れる**

問題

- 同じユーザー情報が何度も保存される
- 更新が大変
- NULLだらけ
- JOINが使えない

---

**✅ 正しい設計**

```
usersテーブル(顧客)
-----------------------------------------
id
name
email

productsテーブル（商品）
-----------------------------------------
id
name
price

ordersテーブル（注文）
-----------------------------------------
id
user_id
product_id
order_date
```

👉 **正規化する**

---

### **② ポリモーフィック・アソシエーション**

**概要**

異なる種類のエンティティを単一の外部キーで参照しようとするアンチパターン

**❌ 悪い設計**

commentsテーブル

| id | comments | target_id | target_type |
| --- | --- | --- | --- |
| 1 | いいね | 10 | post |
| 2 | 最高 | 4 | photo |

```sql
target_type == "post"
→ postテーブルを見る

target_type == "photo"
→ photoテーブルを見る
```

```sql
// post.id なのか photo.id なのか判別できないため、
// 参照整合性を保証できず外部キーを設定できない。
target_id = 10
```

---

**✅ 良い設計
post_comments テーブル**

| **post_id** | **content** |
| --- | --- |
| 10 | いいね |

**photo_comments テーブル**

| **photo_id** | **content** |
| --- | --- |
| 4 | 最高 |

エンティティごとにテーブルを分けることで、
外部キー制約を設定でき、データの整合性を保ちやすくなる。

---

### **③ ジェイウォーク（Jaywalking）**

**概要**

複数の値をカンマ区切りの文字列として単一のカラムに格納するアンチパターン

**❌ 悪い例
articles テーブル**

| **id** | **title** | **tag_ids** |
| --- | --- | --- |
| 1 | Laravel入門 | 2,4,7 |

検索

```
WHERE tag_ids LIKE '%4%'
```

問題

- インデックス(索引)が有効に活用できない
- JOIN不可
- 更新困難

---

### **✅ 正しい設計**

**articles テーブル**

| **id** | **title** |
| --- | --- |
| 1 | Laravel入門 |

**tags テーブル**

| **id** | **name** |
| --- | --- |
| 2 | Laravel |
| 4 | PHP |
| 7 | Web |

**article_tags テーブル（中間テーブル）**

| **article_id** | **tag_id** |
| --- | --- |
| 1 | 2 |
| 1 | 4 |
| 1 | 7 |

中間テーブルを用いることで、記事とタグの多対多の関係を正しく表現できる。

---

### **④ スパゲッティクエリ**

**概要**
複雑で読みにくいSQLクエリ
****

**❌ 悪いSQL**

```sql
/**
SELECT *　のため必要なカラムが不明確で
JOINが多く複雑なクエリは可読性が低下し、
メンテナンスやパフォーマンスの問題を引き起こす可能性がある。
**/

SELECT *
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
JOIN categories c ON p.category_id = c.id
JOIN reviews r ON p.id = r.product_id
WHERE r.rating > 4
AND u.created_at > '2024-01-01'
AND p.price > 1000
```

---

**✅ 改善**

WITH句を使う

**例**

```sql
/**
WITH句を用いることで、レビュー評価条件の処理を分離し、
複雑なJOINを直接書くスパゲッティクエリを避け、
可読性と保守性を向上させることができる。
**/
WITH high_rating_products AS (
  SELECT product_id
  FROM reviews
  WHERE rating > 4
)
SELECT *
FROM products
JOIN high_rating_products
```

**補足**

**WITH句とは**
SQL内で一時的なテーブル（仮想テーブル）を作成し、
その結果を後続のクエリで利用できる仕組みである。
複雑なクエリを分割できるため、可読性や保守性を向上させることができる。

---

### **⑤ マジックナンバー**

**概要**

コード内に直接数値リテラルを埋め込むアンチパターンです。

**❌ 悪い例**

```sql
SELECT *
FROM orders
WHERE status = 3
```

問題

```
3って何？
```

---

**✅ 良い例**

アプリ側

```sql
// 数値の意味が分かるように、定数として定義する（マジックナンバー対策）
const ORDER_STATUS_SHIPPED = 3
```

---

### **⑥ カーゴカルトプログラミング**

**概要**

理解せずにコードやテクニックを模倣するアンチパターン

**❌ 例**

```sql
SELECT *
FROM users
WHERE id IN (
  SELECT user_id
  FROM orders
)
```

理由

```
みんなIN使ってるから
```

しかし

```
JOINの方がクエリの処理時間（実行時間）が短くなる可能性が高い
```

---

**正しい**

```sql
/**
JOINを用いることでテーブル間の関係を明確に表現できる。
また、DISTINCTを使用して重複データを除去することで、
取得したいデータの意図を明確にすることができる。
**/
SELECT DISTINCT users.*
FROM users
JOIN orders
ON users.id = orders.user_id
```

**余談**
データ量が多いほど処理速度の差が出るみたいです。

| **データ量** | **差** |
| --- | --- |
| 100件 | ほぼ同じ |
| 1万件 | JOINが少し速い |
| 100万件 | JOINがかなり速い |

**理由**
```
IN
↓
サブクエリ実行
↓
結果を比較

JOIN
↓
テーブル同士を直接結合
↓
インデックス使いやすい
```

---

### **⑦ プレマチュアオプティマイゼーション**

**概要**

必要以上に早く最適化を行うアンチパターン

**❌ 例**

テーブル作成

```sql
-- 必要以上にインデックスを作成している例（プレマチュアオプティマイゼーション）
CREATE INDEX idx_user_email
CREATE INDEX idx_user_email_created
CREATE INDEX idx_user_email_status
CREATE INDEX idx_user_email_login
```

必要以上にインデックスを作成するとデータ更新時の負荷が増加するため注意が必要。

---

**正しい**

```
実際にパフォーマンスの問題が発生してから最適化を行う。
```

---

### **⑧ EAV（Entity Attribute Value）**

**概要**

フレキシブルなデータモデル（属性を自由に追加できるようにするため）を実現するために使われるアンチパターン

**❌ 悪い設計
product_attributes テーブル**

| **product_id** | **attribute** | **value** |
| --- | --- | --- |
| 1 | color | red |
| 1 | weight | 10kg |
| 1 | height | 20cm |

問題

- JOIN地獄
- 検索遅い
- ENVの値はすべて文字列として扱われるため、データ型が保証されない

---

**正しい**

productsテーブル

| **id** | **color** | **weight** | **height** |
| --- | --- | --- | --- |
| 1 | red | 10kg | 20cm |

属性をカラムとして定義することで、データ構造が明確になり、
クエリの可読性やパフォーマンスを向上させることができる。

---

### **⑨ フェールオープン**

**概要**

エラー発生時にアクセス制限を緩和してしまうというセキュリティに関連したアンチパターン

**❌ 悪いコード**

```sql
if (error) {
  return true;  // アクセス許可
}
```

問題点

```sql
エラー時でもアクセスが許可される
↓
本来アクセスできないユーザーが
処理を実行できてしまう可能性がある
```

SQL例

```sql
// ユーザーが見つからない場合
if(user_not_found){
  allow_access() // 本来は拒否すべきなのに許可している
}
```

問題点

```
ユーザー確認に失敗
↓
本来なら拒否
↓
しかし許可してしまう
```

**✅ 正しいコード**

```sql
// エラーが発生した場合はアクセスを拒否する
if (error) {
  return false;  // アクセス拒否
}
```

SQLイメージ

```sql
// ユーザーが見つからない場合
if (user_not_found) {
    deny_access()  // アクセス拒否
}
```

セキュリティ設計では、エラー時はアクセスを許可するのではなく
拒否する設計にすることが重要。
